---
description: PRをレビューし、バグ・規約違反から設計・可読性の改善提案まで重要度付きで指摘する（単一エージェントで完結、サブエージェントは使わない）
argument-hint: [owner/repo/pull/number] [--comment]
allowed-tools: Bash(gh pr view:*), Bash(gh pr diff:*), Bash(gh pr comment:*), Bash(gh api:*), Read, Glob, Grep
---

$ARGUMENTS で指定された Pull Request をレビューする。

**重要な設計方針:** このコマンドは `Task`（サブエージェント起動）を一切使わない。理由: ヘッドレスCI実行（`claude-code-action`）では `allowed-tools` は「自動承認リスト」に過ぎず、リストに無いツールを呼ぶと人間の確認が取れず自動的に拒否される（`permission_denials_count` が増える）。`Task` は非対話環境で信頼できないため、このコマンド自身の中で完結するステップだけを使う。

## 手順

1. **事前チェック**
   `gh pr view <PR> --json state,isDraft,title,body,comments,headRefOid` で以下を確認し、該当すれば即座に終了する（以降の処理をしない）。
   - PR が closed である
   - PR が draft である
   - 明らかにレビュー不要（自動生成PR、typo修正など自明に問題ない変更）
   - 取得した `headRefOid` に対して、既に `<!-- claude-review-sha: <headRefOid> -->` を含む claude (bot) のコメントが存在する（＝この commit は既にレビュー済み）
     - **注意:** 「claude (bot) がコメント済みかどうか」だけで判定しないこと。新しい commit が push されると `headRefOid` が変わるため、過去のレビュー時のマーカーとは一致せず、正しく再レビューされる

2. **差分の把握**
   `gh pr diff <PR>` で差分を取得する。必要に応じて `Read` / `Grep` / `Glob` で差分周辺のファイルを読み、文脈を補う（変更されていない既存コードとの整合性確認のため）。
   ルートの CLAUDE.md（`@AGENTS.md` 経由で AGENTS.md を含む）はセッション開始時に自動で読み込まれているので、追加で読む必要はない。
   差分が `nari-note-backend/` に及ぶ場合は `nari-note-backend/Documents/backend-implementation-guide.md`、`nari-note-frontend/` に及ぶ場合は `nari-note-frontend/docs/implementation-guide.md`、`infrastruture/` に及ぶ場合は `infrastruture/AGENTS.md` も規約として参照してよい。
   `nari-note-frontend/src/lib/api/` の `types.ts` / `endpoints.ts` / `hooks.ts` / `server.ts` は `scripts/api-generator.py` の生成物なので、手編集の痕跡が無い限りレビュー対象から外してよい。

3. **レビュー観点**
   差分を読み、以下の観点で指摘を洗い出す。各指摘には重要度ラベルを付ける。「確実なバグ」に限らず、レビュアーとして伝える価値がある指摘は積極的に挙げる。

   | ラベル | 対象 | 例 |
   | --- | --- | --- |
   | `[必須]` | マージ前に直すべきもの | ロジックエラー、例外・null の扱い漏れ、セキュリティ（認可漏れ・入力検証・情報漏えい）、データ不整合、CLAUDE.md / 各実装ガイドの規約違反 |
   | `[推奨]` | 直した方がよいもの | 特定の入力・状態で起きる不具合（再現条件を書ける場合）、性能（N+1・不要な全件取得・不要な再レンダリング・キャッシュの invalidate 漏れ）、レイヤー責務のずれ、エラーハンドリング・ローディング表示の不統一、重複コード、分かりにくい命名、型の甘さ、変更に対するテストの不足、ドキュメントとの食い違い |
   | `[提案]` | 任意の改善 | より簡潔な書き方、既存の共通部品・ユーティリティの再利用、読みやすさの改善 |

   指摘の書き方:
   - 「何が」「なぜ問題か（起きうる具体的な状況）」「どう直すか」を書く。`[推奨]` 以上で不具合を指摘する場合は、再現する入力・状態を具体的に示す
   - 既存コードを `Read` / `Grep` で確認してから指摘する。確認できない推測は「〜の可能性がある（未確認）」と明記する
   - 規約違反は該当ルールを引用し、ルールの適用範囲（ファイルパス・スコープ）であることを確認する

   以下は **指摘しない**:
   - リンター・フォーマッタ・型チェックが検出する問題
   - コード中で明示的に抑制されている問題（lint の抑制コメントがある等）
   - 今回の差分と関係しない既存の問題（差分の行やその呼び出し元・呼び出し先に影響するものは対象）
   - `scripts/api-generator.py` の生成物の中身（生成元のテンプレートや Controller / DTO 側で指摘する）

   件数の目安: インラインコメントは合計 15 件まで。超える場合は重要度の高いものを優先し、残りはサマリコメントに一覧で載せる。

   **学びのポイント（任意）**
   修正を求める指摘とは別枠で、次の3カテゴリそれぞれ最大2件まで「学びのポイント」を添えてよい。断定調ではなく説明調で書く（「〜が誤り」ではなく「〜という理由でこの書き方になっていると思われる」）。該当箇所が無いカテゴリは無理に書かない。
   - **ソフトウェア設計**: レイヤー責務の分離、抽象化の粒度、依存の向きなど
   - **パフォーマンス**: EF Core のクエリ、TanStack Query のキャッシュ・再フェッチ設計、レンダリングなど
   - **その他**: 上記に当てはまらないが、学びになる点

4. **出力**
   まずレビュー結果をターミナルに要約する。重要度ごとに件数と各指摘の要点を示す。`[必須]` が 1 件以上あれば「要修正」、無ければ「マージ可（推奨・提案あり）」または「問題なし」と判定する。

   `--comment` 引数が **無い** 場合はここで終了する。GitHubへのコメント投稿は行わない。

   `--comment` 引数が **ある** 場合:
   - 各指摘を `gh api repos/<owner>/<repo>/pulls/<number>/comments` (POST) でインラインコメントとして投稿する（詳細は後述）。学びのポイントも同様にインラインで投稿する。
   - **最後に、指摘の有無にかかわらず必ず** `gh pr comment <PR> --body "..."` でサマリコメントを1件投稿する。このコメント冒頭の `<!-- claude-review-sha: ... -->` が「この commit はレビュー済み」の目印になり、次回 synchronize 時の事前チェック（手順1）がこれを見て再レビューの要否を判定する。**このマーカーを省略すると次回以降レビューが二度と走らなくなるので、必ず含めること。**

     サマリコメントの形式:
     ```
     <!-- claude-review-sha: <headRefOid> -->
     ## Code review

     **判定: 要修正 / マージ可（推奨・提案あり） / 問題なし**

     | 重要度 | 件数 |
     | --- | --- |
     | 必須 | N |
     | 推奨 | N |
     | 提案 | N |

     ### 概要
     <PR 全体に対する所感を 2〜4 行。変更の妥当性、気になった全体的な傾向、良かった点>

     ### 指摘一覧
     - [必須] `path/to/file:行` <一行要約>
     - [推奨] ...
     （インラインに載せきれなかった指摘もここに含める）
     ```
     指摘が無い場合は「指摘一覧」を省略し、概要に確認した観点を書く。

     各指摘のインラインコメントは以下のコマンドで投稿する:
     ```
     gh api repos/<owner>/<repo>/pulls/<number>/comments \
       -f body="<コメント本文>" \
       -f commit_id="<PRのhead commit SHA>" \
       -f path="<ファイルパス>" \
       -F line=<行番号> \
       -f side="RIGHT"
     ```
     - 本文の先頭に重要度ラベル（`**[必須]**` / `**[推奨]**` / `**[提案]**`）を付ける
     - `commit_id` は `gh pr view <PR> --json headRefOid -q .headRefOid` で取得したPRのhead commitのSHAを使うこと（ベースブランチのSHAではない）
     - 小さく自己完結した修正であれば committable suggestion を含める。修正がその提案だけで完全に完結する場合のみ使うこと（追加対応が必要な場合は提案ブロックを付けない）
     - 1つの問題につき1コメントのみ。同じ問題が複数箇所にある場合は代表箇所に1件投稿し、他の箇所を本文に列挙する
     - 規約違反を指摘する場合は該当ドキュメントへのリンクを含める
     - `gh api` がエラーを返した場合（行が diff の範囲外など）はその行へのインライン投稿を諦め、サマリコメントの指摘一覧に含める（無理にリトライしない）

   - 学びのポイントは本文の先頭にカテゴリラベルを付けて投稿する。committable suggestion は付けない。
     ```
     **[学びのポイント / ソフトウェア設計]** <説明>
     **[学びのポイント / パフォーマンス]** <説明>
     **[学びのポイント / その他]** <説明>
     ```

## 注意事項

- GitHubとのやり取りは `gh` CLI を使うこと。WebFetch は使わない
- コード中のリンク（例: 該当箇所への参照）を貼る場合は、必ずフルの git commit SHA を使うこと。`gh pr view <PR> --json headRefOid -q .headRefOid` で取得できる。省略形やコマンド埋め込みでは Markdown プレビューが正しく描画されない
