# spec/ — 振る舞い仕様

ユーザー視点で「画面・機能がどう振る舞うか」を機能単位で記述した仕様書です。

## 位置づけ

- **実行できない仕様書**です。Gherkin 風の独自 DSL で書いていますが、テストランナーやパーサーはありません。
- **正は実装**です。仕様と実装が食い違っていたら、意図した変更かを確認したうえで、実装に合わせて spec を更新します。
- 機能を追加・変更・削除したら、同じ PR で該当する spec も更新します。未実装の構想は書きません（課題は Issue で管理）。
- 自動テストの代わりではありません。テストの方針は `nari-note-backend/Documents/testing-guide.md` を参照してください。

## 書式

```
Feature "機能名" do
  Scenario "シナリオ名" do
    Given "前提条件" do
      When "操作をすると、" do
        Then "期待する結果"
          .And "追加の期待結果"
      end
    end
  end
end
```

- `Feature` は 1 ファイル 1 つ。ファイル名は機能を表すケバブケース（例: `article-edit.spec`）。
- `Given` / `When` を省略する場合は `None` と書きます（例: 常に成り立つ表示）。
- `Given` はネストして条件を重ねられます（例: ログイン状態 → いいね済み）。
- 前提を複数並べる場合は `Given "A".And "B"` のように `.And` でつなぎます。
- 補足や背景は `#` コメントで書きます。

## 書き方の指針

- ユーザーから見える振る舞い（表示・遷移・結果）を書き、実装の詳細（コンポーネント名、API パス）は書きません。
- 主要なシナリオに絞ります。文字数上限・ファイルサイズ・件数などの具体的な値は腐りやすいので、必要なら「値の正はどこか」をコメントで示します。
- 権限による振る舞いの違い（未ログイン / メールアドレス未認証 / 本人以外）は明示します。
